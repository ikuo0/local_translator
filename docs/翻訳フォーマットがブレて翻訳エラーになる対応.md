今回のエラーは、LLMに翻訳だけでなく、**データ構造の維持まで担当させていること**が原因です。

IDやプレースホルダーを正確に維持するよう指示しても、LLMである以上、欠落・重複・改変を完全に防ぐことは難しいです。

対策としては、翻訳処理と構造管理を分離し、LLMが間違えてもプログラム側で復旧できる仕組みにするのがよいと思います。

## **1. JSON Schemaによる構造化出力を使う**

Ollamaには、出力形式をJSON Schemaで制約する機能があります。IDを通常の文章として出力させるよりも、構造を維持しやすくなります。

例えば、行IDをJSONのキーにして、必須キーとして指定します。

入力：

```
{
    "1": "The following format is supported.",
    "2": "The file contains [[KEEP_6]].",
    "3": "Coordinates are defined in inches."
}
```

出力を制約するJSON Schema：

```
schema = {    "type": "object",    "properties": {        "1": {"type": "string"},        "2": {"type": "string"},        "3": {"type": "string"},    },    "required": ["1", "2", "3"],    "additionalProperties": False,}
```

Ollama呼び出し：

```
response = ollama.chat(    model="qwen3:8b",    messages=messages,    format=schema,    think=False,    options=options,)
```

Ollamaの構造化出力は、単なるプロンプトによる指示ではなく、生成時に出力形式を制約する機能です。

これにより、正常に生成が完了すれば、IDの改変やキーの欠落を防げます。ただし、翻訳内容の取り違えやマーカーの欠落までは保証されません。

## **2. 行単位で検証し、異常な行だけ再翻訳する**

ページ全体を失敗扱いにする必要はありません。

例えば、以下の結果が返ってきたとします。

| ID | 原文のマーカー | 翻訳後のマーカー   | 判定 |
| -- | ------- | ---------- | -- |
| 1  | なし      | なし         | 正常 |
| 2  | KEEP_6  | なし         | 異常 |
| 3  | なし      | なし         | 正常 |
| 4  | KEEP_7  | KEEP_7 × 2 | 異常 |
| 5  | KEEP_8  | KEEP_8     | 正常 |

この場合、2と4だけを再翻訳します。

マーカーの検証には `Counter` が利用できます。

```
import refrom collections import Counterdef validate_markers(src, dst):    pattern = r"\[\[KEEP_\d+\]\]"    return (        Counter(re.findall(pattern, src))        == Counter(re.findall(pattern, dst))    )
```

個数も比較するので、欠落・重複・別マーカーへの置き換わりを検出できます。

## **3. 最終リトライではIDもマーカーも送らない**

ここが重要です。

どうしても翻訳できない行については、翻訳対象をさらに分割します。

原文

The header [[KEEP_6]] must be followed by a newline.

プログラム側で分割

The header

翻訳対象

[[KEEP_6]]

翻訳対象外

must be followed by a newline.

翻訳対象

プログラム側で再結合・復元

ヘッダー。。。。。。の後には改行が必要です。

分割翻訳なので日本語の語順が不自然になる可能性はありますが、構造の破損は回避できます。

また、1行だけ翻訳する場合は、そもそもIDをLLMに渡す必要がありません。

## **4. 翻訳処理全体の推奨フロー**

## **対策の優先順位**

| 対策                 | 効果       | 実装負担 |
| ------------------ | -------- | ---- |
| JSON SchemaによるID固定 | 高い       | 小    |
| 行単位のマーカー検証         | 高い       | 小    |
| 異常行のみリトライ          | 高い       | 小    |
| 1行単位の翻訳            | 高い       | 小    |
| マーカー前後の分割翻訳        | 構造維持には高い | 中    |

今回のエラー件数であれば、翻訳方式全体を変更するより、**ページ単位の一括翻訳を維持し、異常があった行だけIDなしの個別翻訳に切り替える**のが、処理速度と信頼性のバランスがよいと思います。

JSON SchemaについてはQwen3:8bでの実際の動作検証はしていませんが、Ollama自体が提供している機能なので、試す価値は十分あります。
